## Context

Сейчас корень композиции размазан:

- `main.cpp` создаёт `Encoders`, `Chassis`, `CommandReceiver`, `Telemetry`,
  `MotorController`, `BtConfigurator`;
- `Chassis` сам конструирует два `Motor` из пинов, зашитых в `chassis.cpp`,
  и держит `Encoders&` только чтобы передать `left()/right()` в моторы и
  вызвать `encoders_.init()`; больше энкодеры в шасси не используются;
- `Motor` получает знак колеса аргументом конструктора и передаёт его в
  `Encoder::measureSpeed(dt, direction)` на каждом такте;
- пины энкодеров живут в `encoders.cpp`, пины моторов — в `chassis.cpp`,
  параметры привода — в `drive_config.h`, параметры связи — в `app_config.h`.

Ограничения: ATmega328P, C++11, без динамического выделения; ISR энкодеров —
`PCINT1_vect` (PORTC, A0–A5); протокол и телеметрия должны остаться
совместимыми, включая знаки полей `ack`.

## Goals / Non-Goals

**Goals:**

- Сделать `main.cpp` единственным корнем композиции и единственным местом,
  где пины привязаны к объектам.
- Убрать знак из энкодера; знак колеса определяется типом колеса.
- Убрать из `Chassis` зависимость от энкодеров.
- Свести конфигурацию в `app_config.h`; удалить `drive_config.h`.
- Сохранить поведение и знаки телеметрии бит-в-бит.

**Non-Goals:**

- Не менять протокол, период телеметрии, ПИД, EMA, watchdog, `stop`/
  `power_stop`.
- Не менять распиновку и проводку.
- Не вводить отдельный `encoderSign`/`driveSign` (см. Open Questions).
- Не трогать `millis()` внутри `Chassis`, мёртвый `kOmegaMaxRadS`,
  инициализацию `prevState_`.
- Не чистить остальные «магические числа» (`bt_config.cpp`, `255`) — это
  отдельное изменение.

## Decisions

### 1. `main.cpp` — корень композиции, `app_config.h` — распиновка

Пины и параметры привода лежат в `app_config.h` как `constexpr`. `main.cpp`
создаёт объекты в порядке:

```
Encoder left/right → Encoders → LeftMotor/RightMotor → Chassis
```

`Chassis` получает два `Motor&` и больше не включает `encoders.h`. Моторы
получают `Encoder&` в конструкторе. `Motor::init()` (новый) настраивает свои
три пина и выполняет `coast()`; `Chassis::init()` вызывает `init()` обоих
моторов.

`drive_config.h` удаляется; `kVMaxMmS` и `kWheelbaseMm` переезжают в
`app_config.h` с `constexpr`. `app_config.h` начинает включать `<Arduino.h>`
из-за `A0..A5`. Комментарий в `controller.py` со ссылкой на
`drive_config.h` обновляется на `app_config.h`; значения там пока остаются
дублированными.

### 2. `Encoders` остаётся, но как группа порта

`Encoders` — не контейнер приводов, а владелец PORTC/PCINT1:

- конструктор принимает `Encoder& left, Encoder& right`;
- `init()` вызывает `initPins()` у обоих и включает `PCIE1`;
- `handleInterrupt()` читает `PINC` один раз и передаёт снимок обоим;
- `ISR(PCINT1_vect)` остаётся в `encoders.cpp`;
- `extern Encoders encoders` остаётся, определение — в `main.cpp`.

`Encoder` хранит свои пины и маски, `initPins()` настраивает `pinMode` и
`PCMSK`, `updateFromPort(portBits)` приватный, `friend class Encoders`.
Статический реестр экземпляров не вводится: вместо скрытого синглтона —
один явный глобальный объект, как сейчас.

Альтернатива — `Encoders` владеет двумя `Encoder` и отдаёт `left()/right()` —
отклонена: пины энкодеров уехали бы из `main.cpp`, а интерфейс группы
разросся бы.

Ограничение «оба энкодера на PORTC (A0–A5)» фиксируется комментарием рядом с
распиновкой в `app_config.h`/`encoders.h`. `static_assert`-проверка
отклонена как лишняя по решению владельца проекта.

### 3. `Encoder` без знака; знак применяется на границах `Motor`

`Encoder::measureSpeed(dtSec)` возвращает мм/с в системе энкодера. `Motor`
переводит на двух границах:

```text
измерение: measured = sign_ * encoder.measureSpeed(dt)   // энкодер → робот
выход:     motorCmd = sign_ * pwmCmd                    // робот → мотор
```

Контур и телеметрия остаются в системе робота. Это сохраняет `mL/mR`,
`oL/oR`, `iL/iR` без изменений по знаку и величине.

Эквивалентность старому поведению:

- `((delta·mmPerTick)·s)/dt ≡ ((delta·mmPerTick)/dt)·s` — умножение на ±1
  точное;
- EMA линейна, поэтому знак коммутирует с фильтром бит-в-бит;
- `(s>=0 ? u>=0 : u<0) ≡ (s·u >= 0)`, `abs(s·u) = abs(u)`;
- при ровно нулевом ШИМ у левого колеса `IN1/IN2` могут поменяться местами,
  но `ENA=0` — наблюдаемого эффекта нет.

Альтернатива — перенести ПИД в систему мотора и пересчитывать три поля
телеметрии — отклонена: больше умножений и неявная семантика интегратора
без выигрыша.

Глобальный флип `kQuadTable` сохраняется: он калибрует «положительное
направление энкодера = положительное направление мотора».

### 4. `Motor` — база; знак хранится в поле и задаётся наследником

`Motor` — базовый класс с защищённым конструктором, принимающим знак.
Конструкторы `LeftMotor`/`RightMotor` знак не принимают: наследник передаёт
его в базовый конструктор, а базовый инициализирует поле.

```cpp
class Motor {
 public:
  MotorTelemetry telemetry() const;
  void init();

 protected:
  Motor(uint8_t pwm, uint8_t in1, uint8_t in2, int8_t sign, Encoder &enc);

 private:
  friend class Chassis;
  // ...
  const int8_t sign_;
};

class LeftMotor : public Motor {
 public:
  LeftMotor(uint8_t pwm, uint8_t in1, uint8_t in2, Encoder &enc)
      : Motor(pwm, in1, in2, -1, enc) {}
};

class RightMotor : public Motor {
 public:
  RightMotor(uint8_t pwm, uint8_t in1, uint8_t in2, Encoder &enc)
      : Motor(pwm, in1, in2, +1, enc) {}
};
```

`tick()` и `applyPwm()` читают `sign_`; `Chassis` хранит `Motor&` и о типе
колеса не знает. Знак задаётся один раз при конструировании объекта и дальше
не меняется.

Виртуальный `sign()` отклонён: значение — константа типа колеса, а
виртуальный вызов добавил бы vptr (2 байта на объект) и две vtable во flash
без выигрыша. Хранимое поле даёт +1 байт на мотор и нулевой оверхед на
вызов.

Публичный конструктор базового класса защищён: `Motor` в `main.cpp` не
создаётся, только конкретные колёса. Виртуальный деструктор не нужен —
объекты статические, удаление через базовую ссылку не используется.

### 5. Порядок инициализации

```cpp
void setup() {
  Serial.begin(kSerialBaud);
  encoders.init();    // PORTC/PCINT1: pinMode, PCMSK1, PCIE1
  controller.init();  // → chassis.init() → motor.init() у обоих
  if (kEnableBtAutoConfig) bt.init();
}
```

`Encoders::init()` вызывается до моторов: PCINT уже настроен, когда контур
начинает работать. Порядок не критичен, но линеен.

## Risks / Trade-offs

- **Регрессия ISR/счёта энкодеров** → сборка плюс стендовый прогон: вперёд
  `mL,mR > 0`, назад `< 0`, вращение на месте — противоположные знаки,
  ручной проворот — противодействие.
- **Ошибка знака даёт положительную обратную связь** (`oL=oR=255`) → тот же
  стендовый прогон; телеметрия видна сразу.
- **Незаметная потеря счёта при неверном пине** (не на PORTC) → ограничение
  задокументировано; проверка остаётся стендовой.
- **Рост RAM и flash** → замер после рефакторинга: RAM 466 Б (+16 к 450),
  flash 9312 Б (+526 к 8786, 30.3%). Поля пинов и знака стали данными
  объектов, поэтому часть вызовов `pinMode`/`digitalWrite` больше не
  сворачивается в константы. Запас по flash остаётся (~21 КБ).
- **Порядок статической инициализации** → `Encoders` хранит ссылки, не
  объекты; порядок объявления в `main.cpp` задан явно.
- **Расхождение констант с Python** → в этом изменении только путь в
  комментарии; синхронизация значений — отдельная задача.

## Migration Plan

1. Перенести пины и `kVMaxMmS/kWheelbaseMm` в `app_config.h`, удалить
   `drive_config.h`, обновить include в `motor.cpp`/`chassis.cpp`.
2. Ввести `Encoder(pinA, pinB)`, `initPins()` и `updateFromPort()`; убрать
   знак из `measureSpeed`.
3. Переделать `Encoders` в группу порта на ссылках.
4. Ввести базовый `Motor` и наследников; убрать знак из конструктора.
5. Перевести `Chassis` на две ссылки `Motor&`; убрать encoders.
6. Переписать композицию в `main.cpp`.
7. `pio run`; стендовый прогон по сценариям из Risks; сравнить телеметрию
   до/после.

Откат — revert коммита; поведение и конфигурация восстанавливаются вместе с
кодом.
