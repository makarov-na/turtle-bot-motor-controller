## Context

Сейчас `CommandReceiver::parseCommand_()` после разбора `set_speed` проверяет `|v| < 0.05 && |w| < 0.05` и присваивает `Action::PowerStop`. `MotorController` по этому признаку вызывает `chassis_.power_stop()` вместо `chassis_.set_speed()`. Парсер тем самым знает про торможение привода и подменяет валидную уставку.

Такое поведение появилось как обход windup: при уставке 0 интегратор, накопленный при движении, даёт равновесие `out = 0` при `measured = (Ki/Kp)·I` (текущий предел `kPidIntegralLimit = 500`, `Ki/Kp ≈ 0.133`, то есть до ~67 мм/с). Поэтому простое удаление перехвата вернуло бы «робот не останавливается на нуле».

Дополнительно `power_stop()` сейчас недостижим с провода: на проводе есть только `set_speed`, а ноль перегружен.

Ограничения: ATmega328P, C++11, текстовый протокол, один главный цикл, жёсткие лимиты flash/RAM; нельзя добавлять динамическую память и тяжёлые зависимости. Пауза ПК-пульта остаётся на существующей команде `set_speed 0.0 0.0`.

## Goals / Non-Goals

**Goals:**

- Убрать из парсера семантику «ноль = остановка»; парсер разбирает только синтаксис.
- Сделать `set_speed 0 0` обычной нулевой уставкой, удерживаемой PID в состоянии `Run`.
- Добавить явные команды `stop` (выбег) и `power_stop` (торможение 300 мс).
- Сбросить PID-интегратор один раз при переходе уставки колеса из ненулевой в ровно нулевую, чтобы windup не поддерживал движение.
- Сохранить паузу как удержание нуля: ПК-пульт продолжает слать `set_speed 0.0 0.0`.
- Привести спеки и телеметрию в соответствие с новой семантикой.

**Non-Goals:**

- Не чинить замирание `mL/mR/oL/oR` в состояниях `Braking`/`Stopped` — это известное ограничение (описано в документации), отдельная задача.
- Не добавлять в кадр `ack` признак состояния привода.
- Не менять watchdog: потеря связи по-прежнему даёт `stop()` (выбег).
- Не менять коэффициенты PID, FF, EMA и не решать медленную сходимость колёс.
- Не менять команды, которые шлёт ПК-пульт при паузе и выходе.
- Не добавлять аппаратную кнопку аварийного останова.

## Decisions

1. **Грамматика провода: три литеральных вида команд.**
   - `set_speed <linear> <angular>` — ровно два числовых токена;
   - `stop` — ровно один токен, свободный выбег;
   - `power_stop` — ровно один токен, L298N fast stop.
   Всё остальное игнорируется, как сейчас. Имена в snake_case, чтобы не смешивать с `set_speed`; вариант `powerStop` из backlog отклонён ради единообразия и совпадения с именем метода.
   *Альтернатива:* оставить только `set_speed` и добавить необязательный модификатор режима — отклонена, потому что снова смешивает уставку и действие.

2. **`CommandReceiver` — только синтаксис.**
   `Action` остаётся, но определяется исключительно литералом (`SetSpeed` / `Stop` / `PowerStop`), а не значениями чисел. Порог `0.05` удаляется. Для `set_speed` поля `linear/angular` заполняются из строки; для `stop`/`power_stop` — нулями.
   Парсер по-прежнему обновляет `lastCommandMs_`, `watchdogTripped_`, счётчик и эхо последней уставки: это протокольное состояние, а не политика привода.
   *Альтернатива:* убрать `Action` и возвращать «сырые» токены — потребовало бы строкового состояния в `MotorController`; текущий enum проще и не знает про `Chassis`.

3. **`MotorController` — единственное место диспетчеризации.**
   `SetSpeed` → `chassis_.set_speed(v, w)` (включая `0 0`); `Stop` → `chassis_.stop()`; `PowerStop` → `chassis_.power_stop()`. Это продолжает существующий принцип: решение «как остановить» уже принимает `MotorController` для watchdog.

4. **Ноль — обычная уставка.**
   `Chassis::set_speed(0, 0)` остаётся в состоянии `Run`, перебазирует измерение при входе после паузы и передаёт нулевые цели в оба `Motor`. `Motor::tick()` продолжает работать каждые 10 мс, поэтому телеметрия на нуле живая. `power_stop()` больше не вызывается автоматически.

5. **Одноразовый сброс интегратора при переходе в ноль.**
   `Motor::setTarget()` сравнивает новую уставку с текущей: если `targetLinear_ != 0.0f && target == 0.0f`, вызывается новый приватный `resetIntegral()`, обнуляющий `integral_` и `prevError_`. Фильтр EMA, `prevTicks_` и `lastOut_` не трогаются: контур продолжает работать, измерение остаётся непрерывным.
   Повторные нулевые команды heartbeat не сбрасывают интегратор, потому что после первого перехода `targetLinear_` уже равен нулю.
   *Почему не `resetPid()`:* он сбрасывает ещё и фильтр скорости, что на работающем контуре даёт лишний выброс измерения.
   *Почему не anti-windup/back-calculation:* это более крупное изменение закона управления, требующее перетюнинга; одноразовый сброс точно закрывает известный сценарий «ноль после движения». Более общий anti-windup можно сделать отдельным изменением.
   *Почему точное равенство нулю:* `set_speed(0, 0)` даёт ровно `0.0f` для обоих колёс; порог снова сделал бы семантику неявной.

6. **Пауза — удержание нуля.**
   ПК-пульт продолжает слать `set_speed 0.0 0.0` каждые 200 мс. Прошивка держит нулевую уставку контуром; интегратор сбрасывается только на первом переходе, дальше PID может накапливать усилие для удержания. Код `controller.py` для паузы и выхода не меняется.
   *Альтернатива:* пауза шлёт `power_stop` — отклонена решением пользователя; активное торможение остаётся доступно явной командой.

7. **Watchdog не меняется.**
   По-прежнему `stop()` (выбег) после 1000 мс тишины. Новая команда `power_stop` не должна использоваться watchdog'ом: резкое торможение потоком через L298N при обрыве связи признано нежелательным в архивном дизайне.

8. **Телеметрия: счётчик всех команд и обнуление эха.**
   `n` инкрементируется на каждую валидную управляющую команду (`set_speed`, `stop`, `power_stop`). `v/w` — последняя уставка `set_speed`; после `stop`/`power_stop` эхо становится `0`. Кадр по-прежнему отправляется только по таймеру 200 мс.
   *Альтернатива:* оставить `n` счётчиком только `set_speed` — тогда хост не видит подтверждения остановки; для отладки полезнее общий счётчик.

9. **`stop()` и `power_stop()` не меняют своей механики.**
   `stop()` — `Stopped`, цели 0, `coast()`, `resetPid()`. `power_stop()` — `Braking`, цели 0, `resetPid()`, `brake()`, таймер 300 мс с перезапуском на каждый вызов. Меняются только точки входа с провода.

## Risks / Trade-offs

- **Ноль может «гудеть» или слабо колебаться на месте после сброса интегратора.** → Проверить на полу при 120 и 150 мм/с: остановка через `set_speed 0 0`, удержание нуля, пауза/resume. Если появится заметный звон, вынести политику интегратора в отдельное изменение (anti-windup/мёртвая зона), не возвращая перехват нуля.
- **Остановка нулевой уставкой мягче, чем `power_stop`.** → Это осознанно; для быстрого торможения есть явная команда `power_stop`. Отразить в README и документации.
- **Breaking change для внешних хостов.** → Все известные хосты в этом репозитории; ПК-пульт менять не нужно (пауза остаётся нулевой), но его докстринги и спеки обновляются. Внешним хостам, слащим `0 0` как стоп, нужно перейти на `power_stop`.
- **Счётчик `n` меняет смысл.** → ПК-пульт только отображает `n`; проверить, что нет логики, завязанной на «только `set_speed`».
- **Строки `stop`/`power_stop` раньше игнорировались.** → Теперь они валидны и сбрасывают watchdog; опечатки по-прежнему игнорируются и приводят к watchdog-остановке.
- **Телеметрия после `stop`/`power_stop` остаётся замороженной.** → Известное ограничение, вне scope; зафиксировано в документации. Нулевая уставка теперь наоборот даёт живую телеметрию.
- **`set_speed 0.04 0.04` больше не тормозит.** → Теперь это маленькая ненулевая уставка; семантика стала явной.

## Migration Plan

1. Прошить прошивку и обновить документацию одним релизом: после прошивки `set_speed 0 0` больше не тормозит.
2. ПК-пульт не требует изменения команд: пауза и выход продолжают слать `set_speed 0.0 0.0`; обновить только комментарии/спеки.
3. Внешним хостам для быстрого останова использовать `power_stop`, для выбега — `stop`.
4. Откат: вернуть перехват нуля и удалить новые команды; состояние EEPROM/конфигурации не мигрирует.
5. Проверка на железе: `pio run`, `openspec validate --all --strict`, затем прогон на полу (остановка с 120/150, удержание нуля, пауза/resume, watchdog, `stop`, `power_stop`).

## Open Questions

- Нужен ли в будущем признак состояния привода в кадре `ack` (`Run`/`Braking`/`Stopped`) — сейчас вынесено за scope.
- Нужен ли общий anti-windup вместо одноразового сброса — решить после живого прогона.
